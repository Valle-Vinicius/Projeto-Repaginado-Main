1. VISÃO GERAL DO PROJETO
================================================================================

O **Babycare** é um sistema web de gestão de estoque desenvolvido como
projeto (SENAI) para uma empresa especializada em produtos infantis
(fraldas, fórmulas, mamadeiras, termômetros, etc.).

Objetivos do sistema:
  - Organizar o controle de estoque e a gestão de produtos;
  - Integrar setores internos (recebimento, expedição, relatórios) com
    segurança;
  - Rastrear lotes por validade (FIFO - o que vence primeiro sai primeiro);
  - Gerar indicadores (dashboard), relatórios e trilha de auditoria;
  - Controlar acesso por perfis de usuário (Operador, Gerente, Admin).

O projeto é uma aplicação web "monolítica" dividida em duas grandes partes:

  + back-end  -> API REST em Node.js/Express + MySQL (camada de dados);
  + front-end -> páginas HTML, CSS e JavaScript puro consumindo a API.

Não há framework de front-end (React/Vue/Angular): tudo é HTML + CSS + JS
"vanilla". O back-end também serve as páginas estáticas do front-end.

6. BANCO DE DADOS (backend/database.sql)
================================================================================

O schema oficial usado pelo sistema é o arquivo backend/database.sql
(banco de dados chamado "babycare"). Ele foi feito para MySQL 8.0+ e inclui,
no final, uma CARGA DEMONSTRATIVA (produtos "DEMO-*") para popular a
dashboard e os relatórios.

TABELAS:

  1) perfis
       id, nome (OPERADOR_ESTOQUE, GERENTE, ADMINISTRADOR), ativo.
       É a tabela que o token JWT consulta para autorizar as rotas.

  2) departamentos
       id, nome, ativo. Ex.: Estoque, Administração, etc.

  3) usuarios
       nome, email (único), senha_hash (bcrypt - validado com CHECK ' $2%'),
       perfil_id (FK -> perfis), departamento_id (FK -> departamentos),
       ativo, tentativas_login (controle de bloqueio), bloqueado_ate
       (data/hora do bloqueio), ultimo_login_em, criado_em, atualizado_em.

  4) auditorias
       usuario_id (FK, apaga junto em SET NULL), acao (ex.:
       RECEBIMENTO_CONFIRMADO, EXPEDICAO_CONFIRMADA, LOGIN_REALIZADO,
       USUARIO_CRIADO), entidade, entidade_id, resultado (SUCESSO/FALHA),
       detalhes (JSON), criado_em. Índices em usuario e data.

  5) categorias
       id, nome (único), ativo, criado_em.

  6) localizacoes
       id, nome (posição física ex.: "Galpão A - P2"), descricao, ativo.

  7) produtos
       codigo (único, é o "SKU"), nome, descricao, categoria_id (FK),
       estoque_minimo (alerta de reposição), unidade (UN, CX, PCT, KG...),
       possui_validade (flag p/ controle de vencimento), ativo, criado_em,
       atualizado_em.

  8) lotes
       produto_id (FK), numero_lote (ex.: "DEMO-2026-F1-01"), fornecedor,
       documento (nota fiscal), quantidade_atual (o saldo REAL do lote),
       data_validade (para o controle FIFO/vencimento), localizacao_id (FK),
       ativo, criado_em.

  9) movimentacoes
       produto_id (FK), lote_id (FK), usuario_id (FK - quem fez),
       tipo ('ENTRADA' ou 'SAIDA'), quantidade, status ('CONFIRMADA'),
       destinatario (saída), destino (saída), documento, observacao,
       criado_em.

REGRA DE OURO DO ESTOQUE:
  O saldo de um produto é sempre calculado pela SOMA das quantidades dos
  LOTES ativos (quantidade_atual). As movimentações guardam o histórico,
  mas o que vale para o saldo é o lote.

OBSERVAÇÃO IMPORTANTE:
  Existe um segundo arquivo database.sql na RAIZ do projeto (banco
  "babycare_estoque") com uma estrutura DIFERENTE e MAIS ANTIGA
  (usuarios com ENUM de perfil direto na tabela, tabela "auditoria" no
  singular, lotes com "data_entrada/quantidade"). Esse arquivo da raiz não
  é o que o backend atual usa - ele é uma versão antiga/residual.

8. SEGURANÇA DO SISTEMA
================================================================================

  - SENHAS: nunca são armazenadas em texto puro - sempre como hash bcrypt
    (custo 10 a 12).
  - AUTENTICAÇÃO: login devolve um JWT assinado (HS256) com validade padrão
    de 2 horas. Todas as rotas protegidas exigem "Authorization: Bearer".
  - BLOQUEIO DE CONTA: 5 tentativas de senha errada bloqueiam a conta por
    15 minutos (tentativas_login e bloqueado_ate na tabela usuarios).
  - PROTEÇÃO CONTRA TIMING ATTACK: quando o e-mail não existe, o sistema
    compara a senha com um hash "dummy" para que o tempo de resposta seja
    similar ao de um e-mail real.
  - AUTORIZAÇÃO POR PERFIL:
      * OPERADOR_ESTOQUE: acessa dashboard, produtos, estoque,
        recebimentos, expedições, relatórios e auditoria;
      * GERENTE: tudo do operador + gestão de usuários (apenas operadores);
      * ADMINISTRADOR: tudo + criação de qualquer perfil + inativar
        usuários e remover links administrativos caso o perfil não permita.
  - VALIDAÇÃO DE ENTRADA: payloads rejeitam campos desconhecidos, valida
    tipos/tamanhos e data; SQL usa sempre parâmetros preparados ("?") para
    evitar injeção SQL.
  - AUDITORIA: ações importantes (login, recebimento, expedição, criação/
    edição de usuário, alteração de perfil) são gravadas na tabela
    auditorias com usuário, ação, resultado e detalhes em JSON. A página de
    auditoria envia cabeçalhos no-cache para não armazenar dados sensíveis.
  - ERROS CONTROLADOS: o servidor nunca devolve stack traces ou detalhes do
    MySQL para o usuário - apenas mensagens amigáveis e códigos.

9. COMO O SISTEMA FUNCIONA (FLUXO DE UMA REQUISIÇÃO)
================================================================================

Exemplo: um usuário registra uma ENTRADA (recebimento).

   1) O navegador abre http://localhost:3000 -> redireciona para
      /pages/login.html.
   2) O usuário faz login (POST /api/auth/login). O backend valida e-mail/
      senha (bcrypt), gera o JWT e grava "LOGIN_REALIZADO" na auditoria.
      O front salva token e usuário no localStorage/sessionStorage.
   3) O usuário abre recebimentos.html e clica em "Novo recebimento".
      O arquivo recebimentos.js envia:
         POST /api/recebimentos
         Authorization: Bearer <token>
         { tipo: "ENTRADA", produtoId, quantidade, numeroLote,
           fornecedor, documento, dataValidade, localizacaoId, motivo }
   4) A rota recebimentoRoutes.js chama os middlewares:
         verificarToken -> decodifica o JWT;
         autorizarEstoque -> confere se o perfil pode (operador/gerente/admin);
      e então chama o controller estoqueController.registrarMovimentacao.
   5) O controller chama estoqueService.registrarMovimentacao, que valida
      os dados e delega ao estoqueRepository.registrarEntrada.
   6) O repository abre uma TRANSAÇÃO:
         - consulta o produto (com FOR SHARE);
         - encontra ou cria o lote (numero_lote), somando a quantidade;
         - insere a movimentação "ENTRADA/CONFIRMADA";
         - grava a auditoria "RECEBIMENTO_CONFIRMADO";
         - COMMIT (ou ROLLBACK se algo falhar).
   7) O controller responde 201 com os dados; o front atualiza a tela e
      mostra o toast "Recebimento registrado e estoque atualizado."

Para uma SAÍDA (expedição) o mesmo fluxo acontece, mas o repository baixa
os lotes na ordem de validade (FIFO) e rejeita (422) se o saldo somado for
menor que a quantidade pedida.

11. COMO EXECUTAR O PROJETO
================================================================================

Pré-requisitos:
  - Node.js instalado;
  - MySQL 8.0+ (ou MySQL Workbench para importar o script SQL).

Passos:
  1) Importar o banco:
       Abra o MySQL e execute TODO o arquivo backend/database.sql
       (ele cria o banco "babycare", as tabelas e os dados de demonstração).
  2) Configurar o ambiente:
       Crie o arquivo backend/.env com base nas variáveis lidas pelo
       backend/config/env.js:
         PORT=3000
         DB_HOST=localhost
         DB_PORT=3306
         DB_USER=<seu-usuario>
         DB_PASSWORD=<sua-senha>
         DB_NAME=babycare
         JWT_SECRET=<uma-chave-secreta-longa>
         JWT_EXPIRES_IN=2h
  3) Instalar as dependências do backend:
       cd backend
       npm install
  4) Subir o servidor:
       Na raiz do projeto: npm run dev
       (ou: cd backend && npm run dev  -> usa "node --watch server.js")
  5) Acessar:
       http://localhost:3000   -> redireciona para a tela de login.
  6) Criar um usuário:
       Rode o script assistido:
         cd backend
         node database/criarUsuario.js
      Escolha o perfil (OPERADOR_ESTOQUE, GERENTE ou ADMINISTRADOR),
      informe nome, e-mail e senha (mínimo 6 caracteres) e o usuário será
      criado com hash bcrypt + registro de auditoria.
      (Alternativa antiga: o database.sql da raiz insere o usuário
       teste@babycare.com com senha "12345678", porém com o schema antigo.)

Scripts do package.json da raiz:
  - npm run dev   -> starta o backend em modo desenvolvimento (--watch);
  - npm start     -> starta o backend normalmente;
  - npm test      -> roda os testes (node --test).
